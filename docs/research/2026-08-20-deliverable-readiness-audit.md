## “合格可用”的定义（真实使用场景 + 竞赛评审视角）

1. **全流程可演示**：模糊问题澄清 → 计划审批 → 检索（召回 ≥40）→ 筛选
   （top-15 无明显无关论文，卡片带理由）→ 下载（≥10 篇全文）→ 写作（引用规范）→
   核验（≥80% 可核验）→ 模型评估/审查 → 打回一轮收敛 → **导出综述 + 引用清单**。
2. **可观测**：每步状态/耗时/成本可见；评估与审查报告可读；思考过程可查。
3. **可靠**：断线恢复、超时兜底、审批防重入、WS 对账、全流程不崩。
4. **有效果数据**：一次 demo 的指标（耗时/成本/核验率/下载率/评估发现问题数）+
   自建 10-20 条查询手工标注的召回/精度基线。
5. **交付物齐全**：README、runbook、项目文档（附件 2 模板）、300 字简介、
   5 分钟视频、源码+测试 zip。
6. **UI 不丢人**：步骤时间线、产物分组、审批、澄清提示、评估/审查可视化。

## 迭代轮数与时间线估算

节奏：每轮 ≈ 1.5-2 天（plan 0.5 + 实现测试 1 + 真实运行 0.5-1）。

必须轮：① M2-15 + 精度调优（1-1.5 轮）；② 导出 + 结构化展示（1 轮）；
③ 可观测面板 + UI 打磨（1 轮，可与 ② 并行）；④ 效果基准 + 稳定化（0.5-1 轮）；
⑤ 材料（文档/简介/视频/zip，1-1.5 轮，可与 ②③④ 并行）。

合计 **5-7 轮 / 8-12 天**。9/1 前必须并行化，建议：

- 8/20-8/23：M2-15 实现 + 真实运行（含精度调优预留）→ 8/24 精度验收
- 8/23-8/25：导出 + 结构化展示 + 成本/可观测 MVP → **8/25 报名 + 材料初稿**
- 8/25-8/28：UI 打磨 + 效果基准 + 全流程回归（2-3 个目标各跑一遍）
- 8/28-8/31：演示视频录制 + 项目文档定稿 + 材料打包
- 8/31-9/1：缓冲 + 提交

结论：**8/28-8/30 达到“可交付可演示”**；若只保核心（精度 + 导出 + 稳定 + 材料），
**8/26 可到“可用”**。现在最危险的不是开发速度，而是：① 精度不解决演示会翻车；
② 材料（尤其视频）需要真实运行素材，必须等精度/UI 到位后录制，时间不可压缩；
